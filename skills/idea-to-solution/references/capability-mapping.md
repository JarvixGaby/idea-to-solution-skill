# 能力映射

从用户可观察的结果向下分析：`工作目标 → 产品流程 → 核心/可选能力 → 输入输出与依赖 → 可选技术做法`。在搜索前形成能力清单和待验证问题；搜索后沿同一清单回填现成资源和开发缺口。用当前 `decomposition_granularity` 控制停止层级。

先列用户真正接触的对象和动作，例如“已有照片目录 → 找出可审阅的相似组 → 安全处理”，而非先拆成图像向量库、地图服务和去重脚本。为每个核心结果写一个可观察的验收样本；只有会影响仓库选择的底层能力才继续拆。把“手工可确认/自动完成”“自己设备上运行/完全离线”“现有文件夹/迁入新图库”等歧义作为分支，保留到候选比较，不默认为更难的一支。

- `product`：场景、主要结果和少量关键能力。
- `capability`：能力、接口或依赖关系、核心/可选/待定标记。
- `engineering`：只有对候选选择有帮助时，加入平台、数据格式、运行环境及接口约束；不写实现方案或代码。

一个资源可覆盖多个能力；一个能力也可由不同资源、官方 API、服务或流程变化满足。搜索前为能力标注核心/可选和用户确认/推测；搜索后标注“成熟仓库可直接采用”“组件可集成或改造”“已有候选但证据不足”“暂列自行开发或另行解决”。最后一类是当前研究结论，不代表仓库绝对不存在。若发现完整解决方案，将被其覆盖的低层拆解收回；若发现新的平台约束，重新检查能力假设。

按输入来源考虑更直接的现成信号：GitHub 项目更新先看 Releases/API，文章先看 RSS 或浏览器剪藏。来源自带能力若能完成用户结果，应与通用抓取器并列比较，不能因它不是一个新仓库而漏掉。拆解最终要回答“采用整品能省掉什么、还要自己维护什么”，而不是只列功能名。

优先识别会决定路径的约束，例如操作系统、离线要求、数据隐私、已有技术栈、可接受的集成工作量。不要凭空补全所有工程细节。
